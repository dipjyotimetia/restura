The self-hosted Restura is a single Node container that serves the SPA and the `/api/*` proxy on one port. Same Hono app that runs in the Cloudflare Worker — just with Node adapters for CONNECT proxying and native WebSockets.

## Quick start

```bash
docker run -p 3000:3000 \
  -e WORKER_PROXY_TOKEN=$(openssl rand -hex 32) \
  ghcr.io/dipjyotimetia/restura:latest
```

All user data lives in the browser's IndexedDB — the server is **stateless**.

<Aside type="caution" title="Browser access needs reverse-proxy auth">
The token protects `/api/*` for scripted callers, but the stock image's web UI can't send it, so requests from the page are rejected with `401`. For browser use, put an authenticating reverse proxy in front and set `REQUIRE_CF_ACCESS=true` — see [Reverse proxy](/self-hosting/reverse-proxy/).
</Aside>

## docker-compose

```yaml
services:
  restura:
    image: ghcr.io/dipjyotimetia/restura:latest
    ports:
      - '3000:3000'
    environment:
      WORKER_PROXY_TOKEN: ${WORKER_PROXY_TOKEN:?required}
      ENVIRONMENT: production
    restart: unless-stopped
```

The repo ships a [`docker-compose.yml`](https://github.com/dipjyotimetia/restura/blob/main/docker-compose.yml) you can copy.

## Configuration

| Env var | Purpose | Default |
|---|---|---|
| `PORT` | Listen port | `3000` |
| `HOST` | Bind address | `0.0.0.0` |
| `WORKER_PROXY_TOKEN` | Shared token for `X-Restura-Proxy-Token` header from the client | **required in prod** |
| `REQUIRE_CF_ACCESS` | If `true`, trust the `Cf-Access-Authenticated-User-Email` header from your reverse proxy | `false` |
| `ENVIRONMENT` | `development` allows localhost upstream; anything else enforces SSRF guard | `production` |
| `ALLOW_PRIVATE_IPS` | Allow RFC 1918 / link-local upstreams (still blocks cloud-metadata) | `false` |
| `ALLOWED_ORIGIN` | Comma-separated `Origin` allowlist (supports `*` wildcards) | unset = no cross-origin access (same-origin only) |
| `RESTURA_STATIC_ROOT` | Path to the SPA bundle | `/app/dist/web` |

## Auth modes

You have two options:

1. **Shared token** — set `WORKER_PROXY_TOKEN`; callers send it in the `X-Restura-Proxy-Token` header (or `Authorization: Bearer`). The SPA only sends a token baked in at build time (`VITE_WORKER_PROXY_TOKEN`), and the stock image has none — so this mode protects scripted access, but the bundled web UI gets `401`. Use reverse-proxy auth for browser users.
2. **Reverse-proxy auth** — set `REQUIRE_CF_ACCESS=true` and put Cloudflare Access (or any IdP that injects an authenticated email header) in front. The server reads the email from the proxy header and trusts it.

## Internal network access

By default the SSRF guard blocks any RFC 1918 / link-local upstream — even from your self-hosted instance. If you genuinely want to proxy to internal services, set `ALLOW_PRIVATE_IPS=true`. The cloud-metadata blacklist (`169.254.169.254`) stays enforced regardless.

## WebSocket constraints (v1)

The WebSocket ticket store is **per-replica in-memory**. Tickets expire in 30 seconds. If you run multiple replicas behind a load balancer, you need either:

- Sticky session routing for the `/api/ws-ticket` → `/api/ws` flow, or
- A single replica (fine for most internal deployments).

This will be revisited in a future release.

## Rate limiting

Per-replica in-memory token bucket. For multi-replica deployments, put a rate limiter (Cloudflare, nginx, Envoy) in front.

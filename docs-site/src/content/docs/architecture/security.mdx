Restura's security posture is **asymmetric** between platforms by virtue of capability gaps. The UI surfaces "Desktop only" badges on fields whose underlying capability isn't available in the browser. Here's the model.

## At rest

### Desktop

- Encryption keys are persisted via Electron's `safeStorage`, which wraps them with the **OS keychain** — macOS Keychain, Windows Credential Manager, Linux libsecret.
- Stored data (collections, history, environments, secrets) is encrypted with **AES-256-GCM** using a key derived from the keychain-wrapped key.
- Secret-bearing auth fields use the **`SecretRef` handle pattern** (ADR 0007): the plaintext lives in `electron/main/security/secret-handle-store.ts` and the renderer only ever sees a handle (`{ kind: 'handle', id, label? }`). Plaintext is resolved only at wire-signing time in the main process — never enters the Zustand store, persistence layer, or exported collections.

### Web

- Persisted state uses **plaintext IndexedDB** by default and is protected only by the browser's same-origin policy.
- Future: an opt-in passphrase prompt can derive an encryption key via PBKDF2; that UI has not shipped and is not advertised as an available capability.
- mTLS, custom CA, SOCKS, and "Verify SSL = off" are **not** available — the browser sandbox doesn't expose them.

## In transit

### SSRF guards on both Worker and Electron paths

Every outbound URL passes through `shared/protocol/url-validation.ts`, which blocks:

- RFC 1918 (private networks).
- RFC 6598 (CGNAT, `100.64.0.0/10`).
- Link-local `169.254/16` — covers the cloud-metadata endpoint.
- Loopback and IPv6 loopback.
- IPv6 unique-local (`fc00::/7`).
- IPv4-mapped IPv6.

The guard is the **single source of truth** — before the shared-protocol refactor it had drifted between backends.

### DNS-rebind guard (desktop)

The Electron main process additionally enforces a **pre-flight DNS guard**: hostnames are resolved before connecting, and `assertResolvedAddressAllowed` is called against every record returned. Note: this is *pre-flight only* — it does not mitigate a true DNS-rebind that swaps records at TTL=0 between resolve and connect.

### Wire-level auth signing

AWS SigV4, OAuth 1.0a, and WSSE are all signed in the **Worker / Electron main process**, not the renderer. The signature matches the exact bytes the upstream receives — proxying through a layer that re-encodes the body would silently invalidate it.

### Hop-by-hop header sanitisation

`shared/protocol/header-policy.ts` strips hop-by-hop headers (`Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Transfer-Encoding`, `TE`, `Trailers`, `Upgrade`) from both directions and rejects header names with control characters.

### Decompression limits (desktop)

The desktop app decodes compressed responses itself, so it caps the work a hostile server can cause. It decodes at most **3 stacked `Content-Encoding`s** (more are left raw, with a notice above the body). It refuses **zstd** frames that need a window over **8 MB** (RFC 9659). And it checks the **10 MB** response limit after **every** decode stage, so a middle layer can't inflate past it. HEAD, 204 and 304 responses and empty bodies are never decoded. On the web, the runtime's `fetch` decodes responses.

Desktop gRPC calls have the same **10 MB** limit, per message. It is checked before a message is buffered and again after gzip or brotli decompression, so a small compressed message can't expand past it. A message over the limit ends the call with `RESOURCE_EXHAUSTED`.

### HTTP method policy

Any RFC 9110 method token is allowed, but `CONNECT`, `TRACE` and `TRACK` are refused in any casing, on every platform. `CONNECT` would turn the proxy into a raw tunnel, and `TRACE` (and IIS's `TRACK`) echo your request headers, credentials included, back in the response. Imports never fail on a bad method: a denied or invalid one becomes `GET`, with a warning.

Generated code treats the method as untrusted, because valid method tokens can contain shell characters such as `` ` ``, `|`, `&` and `$`. cURL snippets quote any method that isn't plain letters and digits, and PHP and Ruby snippets use single-quoted strings. A shared collection can't hide a command in a "Copy as cURL" snippet.

### Upstream cookies stay off the Restura origin

On the web and self-hosted server, streaming responses (SSE, NDJSON) are passed through the proxy almost as-is. The exception is `Set-Cookie`: as a real header it would make your browser store the upstream's cookies for the Restura site itself. The proxy strips it and sends the cookies in an `x-restura-set-cookies` header instead, which the app reads into its own cookie jar. If the upstream sends its own `x-restura-set-cookies` header, the proxy drops it, so a server can't forge entries into your jar.

The network console lists each response cookie's name and attributes, but replaces the value with `[REDACTED]`. Cookie values are credentials.

### Digest auth

Digest is answered in the shared HTTP core, so web, self-hosted, desktop and the CLI follow the same rules ([ADR 0029](/architecture/adrs/0029-digest-auth-challenge-retry/)):

- The first request carries **no credentials**. Restura only answers a `401` that carries a Digest challenge.
- The challenge is answered only if **every hop** of the redirect chain stayed on the original origin. If any hop left it, the `401` is returned unanswered.
- There is **exactly one retry**, and it shares the request's redirect budget.
- The password is resolved where the request is sent: in the desktop main process for keychain-stored secrets. The hosted proxy refuses keychain handles. Only a hash goes on the wire.
- The desktop app no longer re-sends credentials for 300, 304, 305 or 306 responses. Like the web, it returns them as-is.

**Residual risk:** over plain `http:`, an attacker on the network can strip a SHA-256 challenge and force MD5, and can see the exchange anyway. Use `https:` for Digest-protected APIs.

### NTLM auth (desktop only)

NTLM authenticates a connection, so the desktop app runs the whole handshake on one connection inside the Electron main process ([ADR 0036](/architecture/adrs/0036-ntlm-desktop-fetcher-handshake/)). Web and self-hosted don't send it, and the CLI refuses it.

- The first request carries only a negotiate message, with **no credentials**. After the server's challenge, only an HMAC proof is sent, never the password.
- The handshake is **pinned to one HTTP/1.1 connection**. A second connection is refused before any bytes are written, so the authenticate message can't move to another socket. If the server closes the connection after the challenge, the request fails.
- Credentials go only to the **origin you requested**, never to a redirect target on another origin.

Through an HTTP proxy, NTLM always uses a `CONNECT` tunnel, even for `http:` targets, so a pooling proxy can't move the handshake to another upstream connection.

**Residual risk:** no MIC or channel binding (Extended Protection). Over plain `http:`, or with certificate verification off, an attacker on the network can capture the NTLMv2 response (crackable offline) or relay it. Use `https:` with verification on.

## Renderer lockdown (desktop)

The Electron renderer is sandboxed (`sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`) and pinned down by two policies in `electron/main/main.ts`:

- **Default-deny web permissions** — `setPermissionRequestHandler`/`setPermissionCheckHandler` on the default session reject every web-platform permission except `clipboard-sanitized-write` (copy buttons). Everything privileged goes through the validated IPC surface instead. Growing the allowlist is an explicit, test-guarded change ([ADR 0026](/architecture/adrs/0026-electron-csp-and-permission-hardening/)).
- **CSP** — production loads enforce `default-src 'self' file:` with `object-src 'none'`, `worker-src 'self' file:`, `wasm-unsafe-eval` only (QuickJS), and no `unsafe-eval`. The policy exists twice — a response header in `electron/main/main.ts` and a `<meta>` fallback injected at build time in `vite.config.mts` — and a structural test (`electron/main/__tests__/security-hardening.test.ts`) fails if the two ever diverge.

## Scripts

Pre-request and test scripts run in a **QuickJS WASM sandbox** (`shared/scripts/script-executor.ts`):

- No DOM.
- No filesystem.
- No network escape — `fetch` and `XMLHttpRequest` are absent.
- Memory cap (64 MB per script runtime).
- Execution time cap (5 seconds for synchronous scripts; 30 seconds when a host bridge such as `rs.sendRequest` is in use).

This matters because shared collections might carry scripts from anywhere; the sandbox guarantees they can't exfiltrate or pivot.

## AI assistant — prompt redaction

Before any prompt goes to a provider, the renderer's prompt builder (`src/features/ai/lib/promptBuilder.ts`, using `shared/protocol/ai/redaction.ts`) scrubs sensitive material from the context snapshot:

- Sensitive header names (`Authorization`, `Cookie`, `X-Api-Key`).
- Token-shaped secret values in bodies, and environment-variable values (8+ characters) wherever they appear in the URL, headers or body.

The request URL itself is **not** redacted: the host and path reach the provider as written ([ADR 0010 amendment](/architecture/adrs/0010-ai-assistant-architecture/#amendment-2026-10-31-url-host-redaction-was-never-implemented)). The composer's **Send raw (skip redaction)** switch turns redaction off for a single message.

## Telemetry and privacy

Error reporting is **on by default and can be disabled in Settings → Privacy**. Desktop errors and native crashes go to Sentry only while that preference is enabled; tracing is disabled, `sendDefaultPii` is false, and the scrubber removes request context, hostnames, users, breadcrumb data, stack-frame locals, secrets, and file paths. The same opt-out also controls Sentry Release Health's desktop session data (active installs, crash-free rate and version adoption). Sessions carry a random install ID that isn't derived from the device or user, is never attached to error reports, and is deleted on opt-out ([ADR 0040](/architecture/adrs/0040-random-install-id-for-release-health/)).

For the hosted web app, `/api/telemetry/error` is a redacted, rate-limited, allowlist-only log sink and is never stored or forwarded to a third party. Self-hosted deployments collect no server-side usage telemetry. See [ADR 0027 — Telemetry and privacy-preserving usage signal](/architecture/adrs/0027-telemetry-and-privacy-preserving-usage-analytics/) for the full decision.

## MCP server mode

When Restura acts as an MCP server, every tool response is run through a redactor (`shared/mcp-server/redaction.ts` (applied by `postProcessResult` in `electron/main/handlers/mcp-server-handler.ts`)) that strips secrets by name. `SecretRef` handles are never resolved for the MCP surface — agents see metadata, not plaintext.

## Worker auth gate

The deployed Cloudflare Worker requires one of:

- `WORKER_PROXY_TOKEN` set as a secret, sent by the client as `X-Restura-Proxy-Token`.
- `REQUIRE_CF_ACCESS=true` and a Cloudflare Access policy in front of the Worker.

Local dev bypasses auth only when `ENVIRONMENT=development` **and** either Miniflare is detected or `DEV_BYPASS_AUTH=true` is set in `.dev.vars`. **Never put `DEV_BYPASS_AUTH` in `wrangler.jsonc`** (the deployed config).

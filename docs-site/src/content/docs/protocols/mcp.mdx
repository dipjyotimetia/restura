MCP — the [Model Context Protocol](https://modelcontextprotocol.io/) — is the open standard for letting AI agents talk to tools and data sources. Restura plays both sides.

## As an MCP client

Point Restura at any MCP server and explore it like any other request target.

- **`streamable-http`** transport — the modern wire shape.
- **`http-sse`** transport — older shape; <Badge text="desktop only" variant="caution" /> the web build supports only `streamable-http`.
- **`{{variables}}` in the URL** — autocompleted and highlighted (unresolved names are flagged). Resolved from the active environment and globals at connect time.
- **List tools** — see the server's exposed tool catalogue with schemas.
- **Invoke a tool** — fill in the JSON schema, send, watch the streamed result.
- **Result view** — Pretty / Raw / Tree, a JSONPath query, find, copy, and download for every tool result or error payload.
- **Connection headers** — bulk edit (one `key: value` per line, `//` to disable a row) and an optional description per row; values resolve `{{variables}}`.
- **List prompts / list resources** — for servers that expose them.

### Desktop protocol compatibility

The desktop app connects with the current MCP v2 client. Its automatic version negotiation supports both modern v2 servers and legacy MCP servers during the connection handshake, so saved MCP requests do not need a protocol-version setting.

Legacy negotiation is handled inside the v2 client. Restura does not construct a second SDK client or retry authentication, TLS, DNS/SSRF policy, network, or timeout failures, so those errors remain visible rather than being masked by another connection attempt.

This compatibility path is desktop-only. The web and self-hosted clients retain their existing stateless Worker proxy behavior, and `http-sse` remains desktop-only.

### Web and self-hosted session lifecycle

The web and self-hosted clients send each JSON-RPC message through the `/api/mcp` proxy. They follow the Streamable HTTP lifecycle themselves:

- **Handshake.** `initialize` offers the newest protocol version that the `initialize` handshake supports. This is the same version the desktop SDK offers in its handshake. `clientInfo` reports the real Restura version. The negotiated version is stored and shown next to the connection status. Restura sends `notifications/initialized` before any other request.
- **Version header.** Every request after `initialize` carries `MCP-Protocol-Version` with the negotiated value. `initialize` itself never carries it.
- **Disconnect.** Disconnecting sends `DELETE` with `Mcp-Session-Id` through `/api/mcp/terminate`, so the server can free the session. Servers that answer `405` (termination not allowed) or `404` (session already gone) are treated as success. A reconnect also ends the previous session first.
- **Session expiry.** A `404` on a request that carried a session id means the session expired. Restura re-runs the handshake once, which opens a new session, and retries the request once. If concurrent requests all hit `404`, they share a single re-initialize.
- **Server messages in a reply.** A server can send other messages before its reply on the same SSE stream, such as progress, logging or server-to-client requests. These are returned to the client with the reply (`serverMessages`) instead of being dropped. The web client doesn't answer server-to-client requests. It advertises no client capabilities, so servers shouldn't send them.

<Badge text="desktop only" variant="caution" /> Web limitations:

- There is no standalone `GET` listening stream, so server messages sent outside a request aren't delivered.
- There is no SSE resumption with `Last-Event-ID`. If a reply stream drops mid-call, the call fails.

Use the desktop app for long-lived subscriptions.

After connecting, Restura uses the v2 client's typed operations for every standard request supported by the negotiated protocol era: ping, completion, legacy logging level, tools, prompts, resources (including subscriptions), and v2 server discovery. That preserves the client's protocol-era validation, pagination, caching, and modern HTTP behavior instead of treating a production MCP server as an untyped JSON-RPC endpoint. Non-standard server extensions remain explicit requests so their server-provided JSON-RPC errors can still be inspected.

### Modern server coverage

Restura's v2 test server exercises modern discovery alongside tools, prompts, resources, cache hints, schema-declared request headers, multi-round `input_required` responses, and change subscriptions. The MCP workspace presents the core catalogue and request operations; it does not yet provide a dedicated UI for managing subscriptions.

### Elicitation, sampling and roots <Badge text="desktop only" variant="caution" />

Servers sometimes need something from the client mid-call. The desktop app advertises the `elicitation` (form mode), `sampling` and `roots` (with `listChanged`) client capabilities and answers those requests, both as 2025-era server→client requests and as 2026-07-28 multi-round `input_required` tool, prompt and resource results. In the second case the tool call simply completes once you answer.

- **Elicitation** opens a form built from the server's `requestedSchema` (the same field editor as tool arguments). **Accept** sends the content only after it passes the schema check, which runs in the form and again in the main process. **Decline** and **Cancel** send the matching spec action. Closing the dialog counts as Cancel. URL-mode elicitation is not advertised.
- **Sampling** is never answered automatically. The dialog shows the system prompt, every message, the model preferences and `maxTokens`. You write the assistant response, or click **Draft with …** to fill it in from the provider configured for the [AI assistant](/guides/ai-assistant/). The draft is sent with secret redaction on, and nothing reaches the server until you click **Approve & send**. **Reject** (or closing the dialog) returns a "user rejected" error to the server.
- **Roots**: the **Roots** panel under the connection bar holds a per-connection list of `file://` URIs, saved with the connection. The server receives this list from `roots/list`. Saving an edit sends `notifications/roots/list_changed` to a connected server.

A prompt nobody answers expires after 5 minutes. A server may have at most 8 prompts waiting per connection. Prompts are withdrawn when the server cancels the request or the connection closes. Answers are accepted only from the window that opened the connection. On 2025-era servers the tool call that triggered the prompt keeps its own request timeout (60 seconds by default). If you take longer to answer, that call fails even though the prompt is still open.

The web build cannot receive server→client requests because its Worker proxy is request/response only, so these flows exist only in the desktop app.

The same URL validation, DNS pinning, header policy, and Electron IPC validation apply before the SDK is allowed to connect.

## As an MCP server

Restura can also *be* an MCP server for an agent like Claude. The server ships today but fails closed — it exposes no saved data until collection sync and consent controls land ([progress](/overview/delivery-plan/#plan-mcp-server)).

The stdio server uses the v2 server package with its built-in legacy transport compatibility, so modern and legacy clients are served without retaining the v1 SDK.

The desktop app exposes these tools:

- `list_collections` — enumerate your collections.
- `list_requests` — browse requests inside a collection (filterable by folder).
- `list_environments` — list environments and their currently active variables.
- `get_environment` — fetch one environment's details, with secrets auto-redacted.
- `get_history` — query past request executions with filters and a limit.

Every tool is **consent-gated** — each surface is hidden until you share it — and every response is **redacted** so secrets, tokens, and auth headers don't leak into agent context.

See the [MCP server mode guide](/guides/mcp-server-mode/) for setup.

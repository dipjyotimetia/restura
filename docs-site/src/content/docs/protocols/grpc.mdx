Restura speaks the **Connect protocol** on the web target and **native gRPC** over HTTP/2 (with automatic Connect-protocol fallback) on desktop — no local toolchain either way. JSON encoding is the default; binary protobuf is supported where the server allows.

## Discovering the service

- **Server reflection** — the fastest path. Hit the **Reflect** button and Restura lists available services and methods. Reflection sends the request's enabled **Metadata** and **Auth** (variables resolved), so servers that require credentials for reflection — API gateways, Envoy, Cloud Run with IAM — can be discovered. Credentials stored as secret handles are resolved by the desktop app only; on the web, switch them to an inline value.
- **Upload `.proto` files** — pick one file, several files, or a whole folder (the folder button) and Restura compiles them on the fly. Imports resolve against the other uploaded files (by import path, relative to the importing file, or by file name). The `google/protobuf/*` well-known types (`timestamp.proto`, `empty.proto`, `struct.proto`, …) and `google/api/annotations.proto` / `http.proto` / `field_behavior.proto` are built in. An import that can't be resolved fails the upload with an error naming the missing file.
- **Upload a FileDescriptorSet** — for monorepos that already ship a compiled set (`.binpb`, `.protoset`, `.desc`, `.pb` — e.g. `buf build -o api.binpb` or `protoc --include_imports -o api.binpb`). Well-known types the set leaves out are filled in.

### Saved requests keep their schema

When you save a gRPC request to a collection, Restura stores a snapshot of the schema you loaded — the reflected descriptors, the uploaded `.proto`, or the compiled descriptors of a multi-file / FileDescriptorSet upload — together with the request's timeout. Reopening the request, running it in the collection runner, and exporting it to OpenCollection all reuse that snapshot (exports deduplicate identical snapshots; see [Restura extensions](/reference/opencollection/#restura-extensions)). A saved request without a snapshot falls back to server reflection when it runs on desktop; if the server doesn't offer reflection, the run fails asking you to open the request and reflect or upload a `.proto`.

### Unknown request fields

When the request has a schema (an upload, or reflection descriptors on desktop), the message editor flags JSON keys the method's input message doesn't define — nested, repeated and map-value messages included — as you type, with a **Rename to "…"** quick fix for near misses (`nmae` → `name`) and a **Remove** action. What happens on send follows **Settings → Requests → gRPC → Unknown request fields**:

- **Warn** (default) — the editor shows the warning and the request is sent without the unknown keys.
- **Block** — the send is refused with `INVALID_ARGUMENT` listing the keys and suggestions.
- **Off** — no lint; unknown keys are dropped silently.

The same policy applies to collection runs and to every message of a stream. Previously unknown keys were always dropped silently, so a typo sent the field's default value.

## Wire protocol

The request's **Settings → Wire Protocol** selector is saved with the request (and in OpenCollection exports):

- **Auto** (default) — desktop dials native gRPC and falls back to Connect when the server rejects it; web sends Connect JSON through the Worker (unary, no schema needed).
- **gRPC** <Badge text="desktop" variant="caution" /> — native gRPC over HTTP/2 only, no fallback.
- **gRPC-Web** — binary `application/grpc-web+proto`, for servers behind an Envoy `grpc_web` filter, grpcwebproxy, or any Connect/gRPC-Web server. Unary and server streaming work on web (relayed by the Worker's `/api/grpc-web`, messages streamed as they arrive) and desktop. Needs the schema — reflect or upload a `.proto` first.
- **gRPC-Web text** <Badge text="web" variant="note" /> — the base64 `application/grpc-web-text` variant.
- **Connect** — Connect protocol only.

gRPC-Web has no request streaming, so client and bidirectional streaming need native gRPC on desktop.

### Schema drift

Each snapshot records a content hash and the time it was captured. When you reflect again and the server's schema no longer matches the saved snapshot, the builder shows **Schema changed since saved** with a count of breaking and non-breaking changes. **Details** lists each change with its rule — removed services, methods, messages, fields, enums or enum values; changed request/response types; client- or server-streaming changes; field type, cardinality or oneof changes; and renamed fields, JSON names or enum values (breaking because requests are written as JSON). Additions are non-breaking. **Update snapshot** saves the new schema; **Keep saved** leaves the saved one in place. Until you update, the collection runner keeps using the saved snapshot. An uploaded schema (a `.proto`, a multi-file upload or a FileDescriptorSet) is never replaced by reflection.

## Streaming

- **Unary** — request-response.
- **Server streaming** — single request, streamed responses. Live updates land in the response panel.
- **Client streaming** — multiple requests, single response. <Badge text="desktop" variant="caution" /> for full HTTP/2 streaming; browser fetch limits client streaming on the web target.
- **Bidirectional streaming** — same caveat as client streaming.
- **Collection runs** — the collection runner runs streaming requests to completion. Server streams run on web and desktop. Client and bidirectional streams run on desktop only: the runner sends the request message (a top-level JSON array sends one message per element), then closes the client side. On the web they're skipped.
- **Retries** — the request's retry policy also applies to server streams: a stream that ends with a non-OK status runs again.
- **Stream log** — streamed messages can be searched, filtered by direction, frozen, cleared, and exported as JSON or NDJSON.
- **Long streams** — a stream keeps its most recent 1,000 inbound messages (up to 10 MB of JSON). Older ones are dropped from the Stream tab, the response body and `pm.response.messages`, and a **N earlier messages dropped** notice shows how many.
- **Response** — the **Body** tab offers Pretty / Raw / Tree views, a JSONPath query, find, copy, and download (a streamed response's frames appear as one JSON array, indexed by frame). **Headers** shows the server's leading metadata and **Trailers** the `grpc-status` / `grpc-message` and any trailing metadata.
- **Rich error details** — when an error carries `google.rpc.Status` details (from the `grpc-status-details-bin` trailer or Connect's error JSON), an **Error details** tab decodes them: `BadRequest`, `ErrorInfo`, `RetryInfo`, `QuotaFailure`, `PreconditionFailure`, `DebugInfo`, `RequestInfo`, `ResourceInfo`, `Help` and `LocalizedMessage` as JSON, types from your loaded schema likewise, and anything else as its type plus raw base64 (Connect's `debug` rendering is shown too). Test scripts read the same list as `pm.response.statusDetails`. Works on web, self-hosted and desktop, unary and streaming.
- **Field violations in the editor** — when those details include a `google.rpc.BadRequest`, each rejected field is underlined in the request message with the server's description (nested and repeated paths such as `book.authors[1].email_address` are mapped to the JSON keys you wrote, using the request's schema when one is loaded). The Error details tab lists the violations; click one to jump to the field. A field that is missing from the message is marked on its parent object.
- **`{{variables}}` in the URL** — autocompleted and highlighted (unresolved names are flagged). Resolved from the active environment and globals at call time.

### Deadlines and long-lived streams

Each call has a deadline, set in the **Timeout (ms)** field next to the request tabs. The default is 30 seconds. Streaming methods also have a **No deadline** checkbox, so watch or subscribe streams can stay open until you cancel them. Unary calls and collection runs always have a deadline.

On desktop, a stream with no messages in either direction for 15 minutes is closed. Its activity resets that timer, so a stream that keeps sending messages stays open. Every way a stream can end sends a final status, so the request leaves the streaming state. That includes a deadline, an idle close, and a cancel. Each message can be up to 10 MB; a bigger one ends the call with `RESOURCE_EXHAUSTED`.

## Authentication

**Bearer**, **Basic**, **API Key** (header placement) and **OAuth 2.0** are sent as lowercase metadata. Keychain-stored secrets are resolved in the main process on desktop.

- **Not supported for gRPC yet:** AWS SigV4, OAuth 1.0, WSSE, Digest and NTLM. These need the exact wire bytes or a challenge round-trip that the gRPC transports don't do. The auth tab shows a warning, and Send is blocked with an error rather than sending the call without credentials. As a workaround, set Auth to **No Auth** (on the request and on any folder or collection it inherits from) and put a pre-computed credential in a metadata entry. Inherited folder/collection auth is checked the same way as the request's own, for unary and streaming calls.
- **Custom metadata** — gRPC uses metadata in place of HTTP headers; edit it in the same table as HTTP headers, with bulk edit (one `key: value` per line, `//` to disable a row) and an optional description per row. Values resolve `{{variables}}`. There is no per-entry size limit (multi-KB bearer JWTs are fine); total metadata, including auth, is capped at 16 KiB.

## Scripts

Pre-request and test scripts run for every gRPC call type with the same `rs.*` / `pm.*` API as HTTP ([Scripts](/guides/scripts/)), on web and desktop; the CLI runs unary calls only.

- **Streams** — the pre-request script runs before the stream opens and the test script once it ends. `rs.response.messages` holds every message received (`all()`, `count()`, `idx(i)`, `each(fn)`); `rs.response.code` is the final gRPC status and `rs.response.json()` returns the messages as an array. Each stream also gets one History entry.

- **Edit outgoing metadata** — in a pre-request script, `rs.request.metadata` holds the enabled metadata rows (lowercased keys, `{{variables}}` resolved). Add, change or `delete` keys and the call is sent with the result. Auth metadata is added after the script and isn't visible to it.
- **Assert on metadata and trailers** — in a test script, `rs.response.metadata` (alias of `rs.response.headers`) and `rs.response.trailers` expose the leading and trailing metadata; the raw maps are `response.headers` and `response.trailers`.

```js
// pre-request
rs.request.metadata['x-request-id'] = require('uuid').v4();

// test
rs.test('trailer present', () => {
  rs.expect(rs.response.trailers.get('x-checksum')).to.exist;
});

// test, server stream
rs.test('three updates', () => rs.expect(rs.response.messages.count()).to.equal(3));
```

## Tracing

Restura **auto-injects a W3C `traceparent`** header on every gRPC request by default — useful when your services participate in distributed tracing. Override or disable in the request settings.

## Reflection over the web

The web app reflects through a dedicated route, `/api/grpc/reflection`, which calls the server's `ServerReflectionInfo` with Connect streaming framing (reflection v1, falling back to v1alpha). It works against any Connect-protocol server that exposes reflection. Because reflection is a bidirectional-streaming RPC, the hop from the proxy to your server must be HTTP/2: the self-hosted server negotiates HTTP/2 over TLS automatically, but a plaintext (h2c) server or a gRPC-only server (no Connect protocol) needs the desktop app, which speaks native gRPC.

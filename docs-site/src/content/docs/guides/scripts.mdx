Every request can carry two kinds of script:

- **Pre-request script** — runs before the request goes out. Mutate variables, sign a payload, decide a header.
- **Test script** — runs after the response lands. Assert, extract, set environment variables.

Both run in an **isolated QuickJS WASM sandbox**. No DOM. No filesystem. No arbitrary network. Memory and execution time are capped.

## `rs.*` and `pm.*` — the same API

Scripts use the native **`rs.*`** namespace. For drop-in Postman compatibility, **`pm`** is a live alias of the *same* object — `rs.expect(...)` and `pm.expect(...)` are identical, so existing Postman scripts run unchanged.

When you **import** a Postman collection, its `pm.*` calls are normalized to `rs.*` automatically; on **export**, they're rewritten back to `pm.*` so the output still runs in Postman. (The rewrite only touches real `pm.`/`rs.` identifiers — strings, comments, and regex literals are left intact.)

<Aside type="tip" title="Editor IntelliSense">
The script editors are Monaco with full type definitions registered for the API — you get autocomplete, member completion (`rs.`, `rs.response.`), hover docs, and signature help as you type.
</Aside>

## What's available

- **The API object** — `rs.request`, `rs.response`, `rs.environment`, `rs.globals`, `rs.collectionVariables`, `rs.variables`, `rs.test`, `rs.expect`, `rs.info`, `rs.iterationData`.
- **`chai`-style assertions** — `rs.expect(rs.response.json().name).to.equal('alice')`.
- **JSON / text helpers** — `rs.response.json()`, `rs.response.text()`, `rs.response.code`, `rs.response.responseTime`.
- **`rs.sendRequest(...)`** — fire an ad-hoc HTTP request from inside a script (routes through the same SSRF-guarded proxy as a normal request). Non-secret `{{variables}}` resolve; a token naming a secret variable refuses the sub-request. To send a plaintext secret on purpose, read it in the script and pass the value. A sub-request inherits the parent's headers only on the parent's origin (scheme, host and port). On any other origin, or when either URL can't be parsed, it inherits none of them, and a redirect to another origin drops inherited headers the same way. Headers the script sets itself always stay, and follow redirects like any other request's.
- **`rs.request.metadata`** (gRPC) — edit outgoing metadata in a pre-request script. A token naming a secret variable refuses the send unless the saved entry for that key already has it. Script edits to the request on other protocols aren't applied.
- **`rs.vault`** (desktop only) — async `get(key)`, `set(key, value)` and `unset(key)` on an OS-keychain-backed secret vault (`await rs.vault.get('token')`), so secrets stay out of variables and exports. See [Secrets & vaults](/guides/secrets/).
- **`rs.judge(output, opts)`** (desktop only) — an LLM-as-judge semantic assertion for test scripts. `await rs.judge(rs.response.text(), { rubric: 'Answers the question politely' })` resolves to `{ pass, score, reasoning }` (score 0–1). Options include `reference` (a known-good answer), `passThreshold` (default 0.5), a multi-criteria `criteria` list (`{ name, rubric, weight, gate }`, where a failing gate fails the whole verdict), `samples` (self-consistency, up to 5 judge calls aggregated) and calibration `anchors`. It is available in **HTTP and gRPC test scripts** (not pre-request scripts), and only after you turn on **Enable LLM judge** and pick a **Judge provider** and **Judge model** under **Settings → AI → Semantic assertions (rs.judge)**. Cloud providers need an API key (stored as a keychain handle); local runtimes such as Ollama need a base URL instead. Each call costs tokens and sends `output` (and any `reference`) to that provider. **Redact before judging** is on by default and strips token-shaped secrets from both first; where it isn't enabled, and on web, self-hosted and in the CLI, it rejects with a "not wired in" error. The AI Lab's [`judge` scorer](/guides/ai-lab/#llm-as-judge) uses the same engine.
- **`rs.cookies`** — read the cookie jar, plus an async `rs.cookies.jar()` for get/set/clear.
- **Response headers and cookies** — `rs.response.headers` (`get`, `has`, `all`, `each`, `toObject`) and `rs.response.cookies`, the cookies *this response* set (`get`, `has`, `all`, `toJSON`, `each`, `toObject`; `rs.cookies` is the jar). See [Set-Cookie in scripts](#set-cookie-in-scripts).
- **gRPC metadata and trailers** — test scripts read `rs.response.metadata` (the leading metadata; same as `rs.response.headers`) and `rs.response.trailers` (`grpc-status`, `grpc-message`, custom trailers), each with `get`, `has`, `all`, `each`, `toObject`. Pre-request scripts can edit `rs.request.metadata` (a plain object; `rs.request.headers` is the same object) and the call goes out with your changes. For gRPC streams, `rs.response.messages` (`all`, `count`, `idx`, `each`) holds every message received; the test script runs once the stream ends. See [gRPC scripts](/protocols/grpc/#scripts).
- **`rs.execution`** — runner flow control: `setNextRequest(name)`, `skipRequest()`.
- **`rs.visualizer.set(template, data)`** — render a custom HTML view of the response.
- **`require(name)`** — a curated library set is bundled (see below).
- **Console** — `console.log` writes to the script output panel.
- **Legacy Postman globals** — `postman.setEnvironmentVariable(...)` and friends, plus the old `tests["label"] = true` object style, both still work for scripts written before the `pm.*` API existed. New scripts should prefer `rs.*` / `pm.*`.

### Bundled libraries (`require`)

Full Postman v12 sandbox parity ships a fixed library set you can `require` — no arbitrary npm, but the common ones are there:

`ajv` · `chai` · `cheerio` · `crypto-js` · `csv-parse/sync` · `lodash` · `moment` · `postman-collection` · `tv4` · `uuid` · `xml2js`

```js
const CryptoJS = require('crypto-js');
const sig = CryptoJS.HmacSHA256(rs.request.body, rs.environment.get('secret')).toString();
rs.variables.set('signature', sig);
```

## What's not available

- Raw `fetch` / `XMLHttpRequest` — there's no bare network primitive; use `rs.sendRequest(...)` instead.
- Arbitrary `require` / `import` — only the bundled library set above loads; no reaching into npm or your machine.
- DOM globals and the filesystem.

These limits are deliberate: collections are often shared, and a script in a downloaded collection should never be able to exfiltrate data or reach into your machine. Memory and execution-time caps mean a runaway loop can't take down the app.

## Set-Cookie in scripts

A response can send several `Set-Cookie` headers. Scripts see all of them, the same way on web, desktop, and the CLI:

- `response.headers['set-cookie']` (and `rs.response.headers.get('Set-Cookie')`) is every cookie joined with `", "`. Postman's `get` returns only the last cookie, so this differs.
- `response.setCookies` is a `string[]` with one raw `Set-Cookie` value per cookie.
- `response.cookies` is the same list parsed into `{ name, value, domain, path, expires, maxAge, httpOnly, secure, sameSite }` objects. `rs.response.cookies.get(name)` reads it; if a name repeats, the last one wins.
- `rs.response.headers.all()` and `.each()` give one row per cookie, and `.has('Set-Cookie', value)` matches any single cookie.
- `rs.response.to.have.header('Set-Cookie', value)` passes when any one cookie equals `value`.
- Responses from `rs.sendRequest(...)` carry `setCookies` and `cookies` too.

```js
rs.test('sets a session cookie', () => {
  rs.expect(rs.response.cookies.has('session')).to.be.true;
  rs.expect(response.setCookies.some((c) => c.startsWith('csrf='))).to.be.true;
});
```

## Example: a test script

```js
rs.test('status is 200', () => {
  rs.expect(rs.response.code).to.equal(200);
});

const body = rs.response.json();
rs.test('returns a user id', () => {
  rs.expect(body.id).to.be.a('string');
});

// stash the id for the next request in this collection
rs.environment.set('user_id', body.id);
```

## Example: a pre-request script

```js
const ts = Math.floor(Date.now() / 1000);
rs.variables.set('signed_at', ts.toString());
```

## Example: chaining with `rs.sendRequest`

```js
// fetch a token first, then attach it
const res = await rs.sendRequest({
  url: 'https://api.example.com/login',
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: { user: 'demo', pass: rs.environment.get('pass') },
});
rs.environment.set('token', res.body.token);
```

<Aside title="Scripting vs. workflows">
For bounded multi-step orchestration, a [workflow](/guides/workflows/) is usually clearer than chaining `rs.sendRequest` calls in one script. The current safe OWS profile supports sequential `do`, `set`, `wait`, timeout/cancellation, and binding-only saved HTTP calls; branching, retries, and parallelism are intentionally unavailable.
</Aside>

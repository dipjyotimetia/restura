Auth lives on each request and inherits from the parent collection by default — set it once on the folder, every request below uses it. Schemes whose signature depends on the final URL or body bytes (AWS SigV4, OAuth 1.0a, WSSE) are signed **at the wire** (Cloudflare Worker on web, Electron main process on desktop), so the signature matches the exact bytes the upstream receives. Header-shaped schemes (Bearer, Basic, API Key, OAuth 2.0) are applied before dispatch — in the main process when the secret is a desktop keychain handle.

## Supported schemes

### Bearer

The simplest case: `Authorization: Bearer <token>`. Reads variables: `{{token}}`.

### Basic

Username + password, base64-encoded. Stored as a `SecretRef` (handle, never plaintext in the renderer) on desktop.

### API Key

Choose where the key lives — a header or a query parameter — and its name.

### OAuth 2.0

Four grants supported, all with optional **PKCE**:

- **Authorization code** — full browser-redirect flow. Restura opens the auth URL in a system browser and catches the callback.
- **Client credentials** — service-to-service.
- **Resource owner password** — when you must.
- **Device code** — for CLIs and headless clients.

Token refresh is automatic where supported. Issued tokens live in the encrypted secret store (desktop) or session memory (web).

### OAuth 1.0a

Full HMAC-SHA1 signing per request — useful for legacy APIs (Twitter v1, Magento, Etsy, Tumblr). Nonce and timestamp generated per send.

### AWS Signature v4

For AWS APIs (S3, DynamoDB, EC2, etc.). Pick the region and service; Restura computes the canonical request and signs at the wire. Works for HTTP and SSE; gRPC isn't signed yet, so a gRPC call using it is blocked (see [gRPC authentication](/protocols/grpc/#authentication)).

### WSSE

`X-WSSE` UsernameToken header with `PasswordDigest` (default — fresh nonce and timestamp per send) or `PasswordText`. Common for SOAP-y APIs. Signed at the wire for HTTP requests (not yet for gRPC).

### Digest

HTTP Digest (RFC 7616) works on web, self-hosted, desktop, and the CLI. The first request goes out **without** credentials; when the server answers `401` with a `WWW-Authenticate: Digest …` challenge, Restura retries exactly once with an `Authorization: Digest …` header. Only a hash goes on the wire — never the password.

- Algorithms: `MD5`, `MD5-sess`, `SHA-256`, `SHA-256-sess` (the strongest offered is picked), with `qop=auth` or the legacy no-qop form. `auth-int` and `SHA-512-256` are not supported.
- The retry replays the same method and body, and the digest `uri` is the exact request-target that was sent.
- A `401` that isn't a Digest challenge is returned as-is. If any redirect along the way left the original origin, even one that comes back, the challenge is never answered.
- The retry counts against the same redirect limit as the first request; it doesn't get a fresh one. Digest and redirects also work through a SOCKS proxy on desktop.
- Over plain `http:`, an attacker on the network can strip a stronger challenge and force `MD5`, and can see the exchange anyway. Use `https:` for Digest-protected APIs.
- Desktop keychain passwords are resolved in the main process at send time. Web can't use keychain-stored passwords.
- Digest applies to HTTP (and GraphQL over HTTP) requests. It isn’t used for SSE, WebSocket, gRPC, or GraphQL subscriptions.

### NTLM <Badge text="not yet sent" variant="caution" />

You can select NTLM, fill in the credentials, and they are saved and inherited like any other scheme (several importers also map them). **Restura does not yet perform the NTLM handshake when sending**, so requests go out without an `Authorization` header. Use another tool for these upstreams until support lands — [track progress](/overview/delivery-plan/#plan-digest-ntlm).

### mTLS (client certificates) <Badge text="desktop only" variant="caution" />

Upload a `.pem` / `.p12` / `.pfx` with passphrase; the cert is presented during the TLS handshake.

## Secret handling

Secret-bearing auth fields (tokens, passwords, client secrets, private keys) use a **handle-based pattern**: the encrypted value lives in the Electron main process keychain-protected store, and the renderer only sees a `SecretRef` handle. The plaintext is resolved at the wire, never touches the Zustand store, never lands in an exported collection, never appears in crash logs.

## Inheritance

Auth on a collection cascades to every child folder and request unless overridden. Use the **Inherit auth from parent** option (default) on new requests.

Imported Postman "No Auth" is the exception: Restura's `none` means inherit, so an imported explicit `noauth` request below a configured ancestor, or any request below an unsupported-auth folder, is not sent and the Auth tab shows a "Not sent" banner. See [Postman import](/guides/import-export/#postman-import).

## Tips

- Store API keys as **environment variables** rather than inline on the request — they survive auth-type changes and are easy to swap.
- Use **OAuth 2.0 client credentials** for CI runs — paste the client ID / secret into the [CLI](/reference/cli/) and your collection runs without browser prompts.
- For AWS endpoints, set `AWS_REGION` and the service name once on the collection and reuse across requests.

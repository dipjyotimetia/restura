An environment is a named set of variables. Pick one in the top-right selector and every `{{placeholder}}` in your request resolves against it.

## What you can put in a variable

- **Plain strings** — `base_url`, `team_id`, `version`.
- **Secrets** — `api_token`, `client_secret`. Marking an environment variable "secret" masks it in the UI and in collection exports, but the value is still stored as plaintext — environment variables don't use the `SecretRef` handle pattern. For values that need OS-keychain protection, store them on the request's Auth tab instead (see [Authentication](/guides/auth/)), where supported credential fields can be saved as a `SecretRef` handle.
- **Globals** — workspace-wide values shared by every request. Edit them under **Environments → Globals**, or from scripts with `pm.globals` / `rs.globals`. They're stored as plain values, so keep credentials in environment secrets.

## Variable resolution order

When `{{base_url}}` is encountered, the most specific scope that defines it wins:

1. **Data row** — the current CSV/JSON row in a collection run.
2. **Folder variables** — the nearest folder first, then outer folders.
3. **Collection variables** — defined in the collection's settings.
4. **Active environment** — a sub-environment first, then the environment it extends.
5. **Globals** — workspace-wide values.

Pre-request scripts can set environment, collection and global values before the request is sent. If nothing matches, the placeholder is left as-is so you can spot the typo.

To see what a tab actually resolves, open **Environments → Variables in scope**: it lists every name with its winning value (secrets masked) and the scope it came from.

<Aside>
WebSocket, Socket.IO, SSE, MCP, gRPC and GraphQL resolve their URL and headers against the active environment and globals only — collection and folder variables apply to HTTP requests. The scope inspector shows the narrower set for those tabs.
</Aside>

## Switching environments

- Top-right environment selector switches in one click.
- OWS workflows use their bound saved request's normal environment resolution; they cannot override environments or write environment variables.
- The [CLI](/reference/cli/) accepts `--env <file>` to load an environment file (JSON or YAML) for a CI run.

## Built-in helpers

Postman-compatible helpers work in any `{{...}}` placeholder:

- `{{$randomUUID}}` — fresh UUID per request.
- `{{$timestamp}}` — current epoch seconds.
- `{{$isoTimestamp}}` — ISO 8601 timestamp.
- `{{$guid}}` — alias for `$randomUUID`.

## Tips

- Keep secrets out of collection-scope variables — anyone you share an exported collection with sees those values. Mark a collection variable **Keep local** (in collection settings) to leave it out of every export and of Git sync.
- Use the **environment diff** view (when staging vs production are open side by side) to spot drift.
